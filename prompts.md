## 2026-09-22 — Grand Orchestrator: a genuinely different kind of spec, verified live

- `ai_agents/specs/grand-orchestrator.md` asks for something structurally new: a ReAct meta-agent (LLM-driven tool-calling and routing) sitting on top of the six deterministic sub-agents, with LangGraph `interrupt_before`-based human-in-the-loop and a Pydantic retry wrapper. Unlike the four prior "found on disk" specs, its core technical claims held up under implementation -- `interrupt_before`, `MemorySaver`, `update_state`/`get_state` all work exactly as described. The one real correction: the spec named Llama-3-70B/8B as the routing LLM, which isn't on this Groq account (same class of gap as the vision-model mismatch found on the Fleet Registry Agent) -- but unlike vision, a real smoke test found **tool-calling genuinely works** on `openai/gpt-oss-20b`/`120b`, so this agent could be verified live, not just mocked.
- Read every one of the other five agents' `graph.py` files to find their *real* mutating node names for `interrupt_before` -- the spec's FR 4 only gave three "e.g." examples. Real set: foundation→`creating`; fuel→`creating`,`creating_trip`; maintenance→`creating_log`,`creating_report`,`restocking`; accountability→`creating`; assignment→`executing`; insights→none (it's read-only, confirmed against its own spec's "no write operations" constraint). Added `tests/test_orchestrator_registry.py` to assert these against each graph's real `.nodes` dict, so a future node rename fails loudly instead of silently disabling that agent's HITL gate.
- Architecture: `orchestrator/runner.py`'s `SubAgentRunner` compiles each agent's *unmodified* `build_*_graph()` factory with its own `MemorySaver` + `interrupt_before`, per the spec's "Sub-Agent Immutability" constraint -- zero lines changed in any `agents/*/graph.py`. The orchestrator's own loop does NOT use LangGraph's checkpoint/resume on itself, only on each sub-agent; `OrchestratorSession.approve()/reject()/modify()` resume the sub-agent's own thread, append the observation, and re-invoke the orchestrator graph fresh from its `plan` entry point -- simpler than nesting interrupt/resume across two graph layers, verified live.
- Caught a real bug in my own first pass via the test suite: `execute_tool` was calling `validate_tool_args(..., attempt=1)` hardcoded on every hop, so `MAX_RETRIES` (FR 7) could never actually be reached -- a malformed tool call would retry forever instead of hard-faulting after 2 attempts. Root cause: I was returning bookkeeping keys (`_tool_retry_counts`, `_pending_image_bytes`, `_pending_mime_type`) that were never declared in `OrchestratorState`'s `TypedDict` -- **LangGraph silently drops any key a node returns that isn't declared in the state schema**, it's not an error. Every other agent's state.py already followed this discipline by declaring every field it touches; I broke it here without realizing why it mattered until the retry-exhaustion test's timing came out wrong. Fixed by declaring all three fields explicitly.
- Live-verified end-to-end (not just scripted): "find the worst-health vehicle with no active assignment and assign it to Jane Smith" against a fake backend with the real Groq LLM correctly chained `insights`→`assignment`(conflict check)→`foundation`(resolve odometer)→`assignment`(the write, which paused for approval) -- including a genuine self-correction mid-run when a `driver_history` call failed for a missing `query_driver_id`, recovering by resolving the driver's ID first. `approve()` resumed the real paused thread and completed the write; the synthesis correctly cited the actual created record. A second live session with a `driver`-role token had its fleet-health request correctly refused and explained, not silently bypassed or falsely reported as successful.
- 22 new tests (243 total in `ai_agents/`), all deterministic (scripted fake LLM + fake runner, no network call) except the live verification above, which was run manually and is not part of the committed suite since a live LLM's exact tool choice isn't something `pytest` can assert on deterministically.

## 2026-09-23 — FleetLiveObserver: a spec that conflicted with an existing hard rule

- `ai_agents/specs/fleet-live-observer.md` asked for something that isn't just factually off (like the last several) but actively conflicts with an architectural rule already established for every other agent in this codebase: its §5 "Data Lifecycle & Retention" wants direct PostgreSQL + S3/Parquet persistence from the telemetry hook, but root `CLAUDE.md` and `ai_agents/CLAUDE.md` both say `ai_agents/` never writes to the database directly, only through the backend's REST API -- and no telemetry endpoint exists there. Resolved by making the observer's `sink` an injectable async callable defaulting to local `logging` (which is FR 6's own stated fallback anyway, not a new invention), documented explicitly as a one-line swap once a real backend endpoint exists -- not silently built around, not silently ignored.
- Second real finding: `on_tool_start`/`on_tool_end` don't fire automatically just by attaching an `AsyncCallbackHandler` to a graph run, because `orchestrator/graph.py`'s `execute_tool` node dispatches sub-agents itself (reads `tool_calls` off the LLM response, calls `SubAgentRunner` directly) rather than through LangChain's own tool-execution runtime -- there's no real `Tool.run()` call anywhere for a callback to attach to. `FleetLiveObserver` ended up with two entry points into the same redaction/schema logic: the real `AsyncCallbackHandler` interface (verified against the installed `langchain-core`'s actual method signatures, for a future async execution path) and a plain sync recording API (`record_node`, `start_tool_call`, `record_tool_result`, `record_llm`) that `graph.py` calls explicitly today.
- A subtler redaction correctness issue caught before it became a bug rather than after: `graph.py`'s existing `_format_observation()` builds the LLM-facing scratchpad text via `repr()` on raw sub-agent state -- which the LLM is *supposed* to see unredacted (redaction is for the audit trail, not the model's own reasoning context). Wiring the observer naively off that already-formatted string would have meant nothing was ever actually redactable (a formatted string has no dict keys left to redact by). `record_tool_result()` instead takes the raw sub-agent state (`raw_result`) as a separate parameter and redacts *that* independently for the stored trace, leaving the scratchpad's unredacted text untouched.
- Wired additively: `OrchestratorDeps.observer` defaults to `None`, and every one of the 243 pre-existing tests passes completely unchanged. 36 new tests (279 total in `ai_agents/`), including two end-to-end integration tests proving the observer is actually reached during a real (scripted) orchestrator run -- not just unit-testable in isolation -- and that a HITL pause/resume round-trip correctly shares one `trace_id` across both halves (FR 4: a trace_id is per session *turn*, and approval is part of the turn that paused, not a new one). All passed on the first run.

## 2026-09-23 — Execution Pre-Hooks: a bug in the spec's own acceptance test

- `ai_agents/specs/execution-pre_hooks.md` had its own internal inconsistency: `SecurityConfig.blocked_phrases`' default is the literal substring `"ignore previous"`, but the spec's own AC 1 example text is `"ignore all previous instructions"` -- which does NOT contain that substring ("all" sits between the two words). A naive substring check, built exactly as the config's shape implies, would fail the spec's own acceptance criterion. Fixed by making regex (tolerant of words in between) the primary detection mechanism in `orchestrator/security.py`, keeping `blocked_phrases` as a literal supplementary layer for phrases where exact substring matching is genuinely correct (`"drop table"`).
- AC 2's specific claim doesn't hold given how the orchestrator's own tool schemas are typed: none of the six `TOOL_SCHEMAS` validates `vehicle_plate` strictly -- it lives inside a loosely-typed `dict[str, Any]` field (`assign_request`), which has no per-key validation, so `{"vehicle_plate": "xyz-999 "}` would pass Pydantic validation completely unchanged, normalized or not. Implemented `orchestrator/normalization.py` to genuinely normalize the value (verified directly), but documented that its real benefit is `Literal`-enum case-mismatch prevention and cleaner downstream entity resolution, not preventing the specific `ToolValidationError` AC 2 describes.
- Found a second latent bug while implementing date normalization, not fixed in this pass: `mcp_server/assignment_tools.py`'s `get_vehicle_assignment_history_tool` calls `target_date.isoformat()`, assuming a real `date` object, but the orchestrator's `AssignmentToolInput.query_target_date` (and the assignment agent's own state) both type it as a plain `str` -- using it through the orchestrator would crash with `AttributeError`. Pre-existing, untested until now, flagged rather than patched on this branch -- same treatment as the Fuel Agent's `Driver.id`/`User.id` bug from two specs ago.
- Two more infrastructure gaps resolved the same way as the telemetry spec's Postgres/S3 gap: no Redis exists anywhere in this project (checked `pyproject.toml`, `docker-compose.yml`), so the exact-match cache tier is a real, working in-process `dict`+TTL store (Redis is swappable in later via the same interface); no embedding-generation pipeline exists anywhere either (`memory/vector_store.py` requires a *pre-computed* embedding, nothing computes one), so the semantic-match cache tier is an honest, always-miss `NullSemanticCacheBackend` rather than a crude token-overlap heuristic that could produce a false hit across two different vehicles or drivers.
- Wired additively (`OrchestratorDeps.cache` defaults to `None`); all 279 pre-existing tests pass unchanged. 41 new tests (320 total in `ai_agents/`), including an end-to-end integration suite proving all three hooks actually fire through a real `OrchestratorSession` run -- the security hook blocking before any LLM call, normalization reaching the sub-agent already clean, and a second identical read-only call across two separate session turns correctly bypassing the sub-agent runner entirely. All passed on the first run.

## 2026-09-30 — Cost/latency architecture: tiered model chain, budget breaker, token diet

- **Budget context.** OpenRouter balance $4.87 (was $0, which made the earlier Claude failover reject with 402). Ollama is not installed on this machine, so a local tier can't be verified here.
- **Tiered chain (`core/llm_failover.py`), cheapest first:** optional local Ollama (`OLLAMA_PLANNER_MODEL`, 0.5 s timeout, off unless set) → Groq `gpt-oss-20b` (free) → OpenRouter `gpt-oss-20b` ($0.018/$0.09 per M tokens; the same model already validated here, ~100× cheaper than Claude Sonnet) → a free OpenRouter model. Claude is no longer in the default chain (opt-in: `OPENROUTER_PREMIUM_MODEL` / `ORCHESTRATOR_PROVIDER=openrouter`). Tier 0 without an LLM already exists: the deterministic read/write classifier (`turn_profile.py`) costs $0 and ~0 ms.
- **Budget circuit-breaker (`core/llm_budget.py`).** Each paid call is costed from provider-reported token usage and persisted in `ai_agents/.llm_spend.json` (gitignored); at `LLM_BUDGET_USD` (default $4.50 of the $4.87) paid models are skipped and the chain falls through to free ones; if nothing free is left the turn errors rather than spending. Spend shows on `/health`. Unusable paid replies are still billed.
- **Per-call telemetry.** One log line per LLM call: model, free/paid tier, input/output tokens, cost, latency.
- **Fast failover.** `max_retries=0` (SDK backoff on 429s was silent latency), 12 s cloud timeout, 0.5 s local; a model that returned 402/429 or was unreachable is skipped for 60 s.
- **Token diet.** History window 6 messages (older context is in the memory summary); system prompt rewritten ~35% shorter with the same routing contract, static text first for provider prompt caching; hard output caps (planner 400, synthesis 500; env-tunable); exact tool-result cache now covers all six sub-agents (writes still invalidate); embedding LRU (256).
- **Two measured findings that changed the design.** (1) `gpt-oss` spends 60–80% of its output budget on hidden reasoning, so a tight `max_tokens` left answers empty; `reasoning_effort=low` (Groq param / OpenRouter `reasoning.effort`) cut reasoning from ~100 to ~5 tokens and replies ~60%. This is why the planner cap is 400, not the 150–250 suggested: 250 is safe only with low effort and tool-call JSON. (2) Some OpenRouter hosts of gpt-oss return HTTP 200 with `finish_reason=error` or leak raw `<|channel|>` tool-call markup as the reply (Groq parses it server-side). Those replies now count as failures and fail over.
- **Measured cost:** about $0.00005 per LLM call, ~$0.0002 per turn, so $4.87 ≈ 20k+ turns. OpenRouter's gpt-oss latency is 4–6 s per call versus 0.5–1 s on Groq (provider sort doesn't help), so Groq stays first whenever its daily quota allows.
- **Not done, deliberately:** real token streaming (the graph is synchronous; the SSE layer chunks the finished reply); `asyncio.gather` across sub-agent calls (the graph, HITL and shared state are synchronous; memory reads already run concurrently); semantic (embedding-similarity) response cache (a false hit across two vehicles is worse than a miss; the exact tool-result cache is kept); Tier 2 auto-escalation from a classifier; Redis; Ollama live test.

- **Ask before writing (`orchestrator/required_fields.py`).** Before any non-read call: a typed fuel log needs vehicle, date, odometer and two of liters/price/total (the third is derived); an assignment needs vehicle, driver, start/end odometer and condition (taken/released "now" if no time is given); maintenance, incident and registry writes need document text or a photo. If something is missing the sub-agent is not run and the model gets "NOT RUN -- missing: ..., ask the user"; the reply prompt tells it to ask one short question and say nothing was logged. What only extraction can tell (a work order's odometer or plate) still halts in the sub-agent, and such "Could not determine..." halts are now worded as "needs more information from the user" instead of an apology. Photo receipts are not pre-checked: the photo supplies the fields.
- **Approval cards (`orchestrator/approval_summary.py`).** The paused sub-agent's state becomes labelled rows per agent (fuel: vehicle, date, station, odometer, liters, price, total, notes; maintenance: vehicle, odometer, service type/scale, description, parts, cost; incident; assignment; registry), sent as `hitl_state.summary` with a question per agent; the card renders them as a definition list. Internal ids and tokens are never shown.
- **Verified.** Agents 871 passed, frontend 790 (typecheck and eslint clean). Not re-run live against the models.

## Token diet: trimmed context, compact observations, prompt caching, model routing

**Prompt:** "Our Grand Orchestrator pipeline is consuming up to 8K tokens per turn ... prune history, compress system prompts and tool schemas, enable prompt caching and route cheap models to cheap work, benchmark, commit."

- **Measured first (cl100k).** A planning call carried ~3.7k tokens before any data: tool schemas 3,195, system prompt 345, document prompt 170, image prompt 131. One vehicles list was 1.6k, and every extra hop resent all of it. Sub-agents are deterministic graphs with no LLM system prompt, so only the orchestrator prompts and schemas matter.
- **History.** `HISTORY_WINDOW` (6) now also bounds the in-process `chat_history` (`session.py`, kept to twice the window); inside the window only the last two messages stay whole, older ones are shortened (`shorten_turn`, 700 chars).
- **Observations (`orchestrator/compaction.py`).** Tool results are rendered as compact JSON with empty/bookkeeping fields dropped, and capped at ~800 tokens. Lists are cut *between* records with "...[N more of M records not shown; filter the request ...]" so the model never reads a half record or mistakes a cut for the full set. Document passages are capped the same way.
- **Schemas and prompts.** Tool docstrings and the document/image prompts rewritten tighter (tools 3,195 -> ~2,556; document prompt 170 -> 101; image 131 -> 77) while keeping the phrases the tests and the model rely on (slip keys, service_due, vehicle_make...). Token-budget test lowered to <2,700.
- **Caching.** Static text first, then tools, then per-turn memory and history, so DeepSeek/Groq prefix caching applies automatically. For Anthropic models the static system message gets `cache_control: ephemeral` (auto when ORCHESTRATOR_PROVIDER=openrouter with an anthropic/ premium model; override with LLM_PROMPT_CACHE=on|off). It does nothing on non-Anthropic models.
- **Routing.** Planning, the input guard (safeguard-20b) and vision stay on cheap chains; document retrieval is embeddings + reranker, not a chat model. Optional `SYNTHESIS_PREMIUM_MODEL` runs only the final reply on a stronger OpenRouter model, with the cheap chain behind it as fallback.
- **Verified.** Agents 889 passed. ruff (F,E9,B) clean on changed files; mypy reports the same 16 errors in orchestrator/graph.py and session.py as before this change (none new). Not re-run live against the models.

## Smart field defaulting and single-turn slot filling

**Prompt:** the assistant looped in chat ("odometer?", then "which record type, service_entry?") instead of logging; default obvious fields, ask for all missing ones at once, and run the tool the moment the user answers.

- **Root cause.** `service_entry` exists nowhere in the code: after "odometer 45000" the model lost the original work-order note (the tool takes it as `document_text`) and invented a question. The orchestrator also asked for the date and odometer of typed fuel logs and for the odometer and condition of assignments, which the system can supply itself.
- **Defaults, in the sub-agents.** Maintenance: no odometer stated -> the vehicle's `current_odometer`, noted in the log description (only a vehicle with no reading on file is still asked). Fuel: typed log with no date -> today; no odometer -> the vehicle's last reading (continuity check skipped for the defaulted value, note added); an undated receipt -> today; typed `notes` are kept. Assignment: handover odometer -> the vehicle's last reading, condition -> "good" (the approval card shows both). Never defaulted: vehicle, driver, liters/cost figures.
- **Asking once.** `required_fields` now asks only for what cannot be inferred. Both the "NOT RUN" and "halted, needs input" observations tell the model to ask for ALL missing items in ONE message, and when the user answers to call the same tool again immediately with the earlier details merged in (typed work order: append to `document_text`) and never to ask for a record type. The system prompt was left alone (it is at its token budget); the instruction rides on the observation, where it applies.
- **State merge.** The chat history and scratchpad already carry the earlier details into the next turn, so no runner change was needed; the two-turn test proves the second turn is one planning call straight to the tool and the approval card.
- **Tests.** `tests/test_slot_filling.py` (10): defaults per agent, stated values never overridden, figures never defaulted, ask-once wording, two-turn session ending at `hitl_state`. Five older tests that pinned "ask for date/odometer/condition" were updated.

## Jev (TypeSafe System One) as the first decision layer

**Prompt:** introduce Jev as the primary routing/decision layer in front of the LLM ReAct loop: intent routing via a `choice`, write gating via `noul`, deterministic validation in code, LLM fallback on any failure.

- **What Jev is.** A decision-only model: POST `https://api.typesafe.ai/v1/systemone` `{model: "jev-latest", state, questions}` with a bearer key; a `choice` returns the option with probabilities and confidence, a `noul` a yes/no probability; ~350-600 ms measured. It cannot write text or fill arguments, which shaped the design (checked against TypeSafe's docs and a live call, not guessed).
- **Routing (`orchestrator/jev_router.py`, used in the plan node on the first hop only).** One request asks `route` (fuel_log / maintenance_log / document_search / registry_lookup / complex_reasoning) and `lookup_entity`. document_search -> `search_documents(query=message)`, registry_lookup -> `foundation(query_entity)`, maintenance_log (no photo) -> `maintenance(work_order, document_text=message)`, all dispatched with no planning call and followed by one reply call. fuel_log is not dispatched directly (its arguments need extraction): the planner stays but only the fuel and foundation tools are bound (fewer schema tokens). complex_reasoning and anything doubtful is the unchanged LLM loop.
- **Code keeps the authority.** The route must clear confidence 0.60, be a known route, and pass a role table that mirrors the sub-agents' own write roles (a role outside it goes the LLM path, where the sub-agent's RBAC refuses properly). A photo on a maintenance turn goes to the planner (work order vs parts invoice). Registry needs a confident entity.
- **Write gate (`gate_write`, before any non-read-only sub-agent call, after the existing required-field check).** `noul high_risk` and a `choice` over a per-agent slot list plus "none". A missing slot at >= 0.80 confidence halts with a FIXED sentence (`missing_reply`, no model call: the synthesis node returns `_deterministic_reply` as is) unless the code can see the item is present (plate regex in the note, a non-blank field, a photo). High risk prefixes the approval card prompt with a notice; it never skips the card (every write already ends at human approval). A gate call that fails does not block the write.
- **Fallbacks.** No `JEV_API_KEY`, `JEV_ENABLED=off`, timeout (2 s), 4xx/5xx/429/529, malformed answer, unknown route, low confidence: LLM path. Three consecutive failures open a 60 s breaker so a down Jev costs one fast skip, not a timeout per turn.
- **Typed notes across turns.** Because a direct maintenance route passes the user's words as the note, "odometer 45000" after the question merges with the held-back note via `merge_typed_note` (also trims a doubled period).
- **Tested.** `tests/test_jev_router.py` (41): the request contract, every route decision, RBAC, each failure mode and the breaker, and through a real session that a document question / lookup / maintenance note never reaches the planner, a gate halt makes zero LLM calls, the code overrules a wrong "missing", risk warns without skipping approval, Jev down behaves like before. Live (real key, port 8100): maintenance on a vehicle with an odometer reaches the approval card in one turn; with none, it asks once and "odometer 45000" reaches the card; "show me all our vehicles" is routed directly (one reply call, ~1.7k tokens in vs ~3.7k+ before for the planning call alone).
- **Not verified live:** the document_search route (needs an uploaded document) and the high-risk warning.
