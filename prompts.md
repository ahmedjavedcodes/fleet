The interview surfaced three scope decisions the plan left implicit, confirmed with the user: (1) supplier onboarding gets its own vision-extraction skill (`extract_supplier_doc`), not just vehicles/drivers; (2) update/edit of existing records stays out of scope for this agent (create + read only); (3) a vehicle document missing `fuel_type` (a required backend field no registration card states) is resolved by asking the user in-chat, not defaulting or hard-rejecting.

  - `core/llm_config.py` — added `GROQ` and `LLAMA_API` providers (both OpenAI-compatible endpoints, same lazy-import pattern as the existing three providers).
  - `mcp_server/foundation_tools.py` (not `ai_agents/mcp/`, deliberately — that package name collides with the installed `mcp` SDK on `sys.path`, per the existing `NOTE` in `ai_agents/mcp/server.py`) — the six get/create tool wrappers, each write tool RBAC-gated via `auth_context.can_write` before any backend call.
  - `agents/foundation/` — `state.py` (`FoundationAgentState`), `license_inspector.py`, `duplicate_checker.py`, `router.py` (structural Onboard/Query classification by image presence, not an LLM call — the signal is already unambiguous), and `graph.py` wiring it all into a LangGraph state machine with every external dependency injected via `FoundationAgentDeps` for testability.

## 2026-09-22 — Driver Accountability & Asset Misuse Agent: verified then implemented

- `ai_agents/specs/driver-accountability-agent.md` was already present on disk, unlike the other three agents' specs, which I wrote myself after running the interview/verification pass. This one read like an unverified plan wearing a spec's filename (hedged language like "`GET /api/v1/drivers/safety` (or equivalent analytics endpoints)"), so I checked it against the real backend before implementing rather than trusting the filename.
- Found one finding more serious than any prior agent's: **FR 3 ("Misuse & Geofence Auditing") is architecturally impossible as written.** The root `CLAUDE.md` constraint is explicit — no real-time hardware, IoT, or GPS integration anywhere in this system — and there is no geofence, shift-schedule, or "authorized operating bounds" data model anywhere in the backend to audit against. Reframed as `agents/accountability/misuse_auditor.py`: a plain time-window heuristic over each `TripLog`'s existing `start_time`/`end_time` (flag trips outside a configurable hour window), explicitly documented as a heuristic proxy for human review, not real misuse detection.
- `get_driver_safety_tool` doesn't exist as a backend endpoint (the plan's own hedge was correct to worry). Replaced with `get_driver_timeline_tool` wrapping the real `GET /api/v1/drivers/{id}/timeline` (already aggregates trips/reports/incidents), with the agent aggregating incident counts by severity from that response — a genuine capability instead of a guessed URL.
- RBAC was more permissive in reality than the spec claimed: `/api/v1/incidents`' real roles are `(admin, fleet_manager, driver)` for **both** create and read — a driver can read their own incidents (row-filtered server-side), not just submit them. Only `mechanic` is excluded. Corrected `mcp_server/accountability_tools.py` accordingly rather than implementing the spec's stricter, inaccurate claim.
- `IncidentLogCreate.incident_type` is required and has no field the plan's extraction schema asks for; added it to `IncidentExtraction` with a `damage` default when unmappable (matching the plan's own implicit framing, since its only extraction target was `damage_description`).
- **Found a real bug in the already-shipped Fuel Agent while building this one's driver-impersonation guard correctly:** `Driver.id` is a separate primary key from `Driver.user_id` (which FKs to `User.id`). `agents/fuel/graph.py`'s trip-log path (via `mcp_server/fuel_tools.py`) overrides a driver-role caller's `driver_id` to `context.user_id` — but that's the `User.id` from the JWT's `sub` claim, not the caller's `Driver.id`. `TripLogCreate.driver_id` expects a `Driver.id`. This agent's own driver-impersonation guard (`_own_driver_id` in `agents/accountability/graph.py`) does it correctly: looks up the `Driver` row whose `user_id` matches the caller's `user_id` first. The Fuel Agent's bug was **not** fixed in this pass — flagged to the user as a follow-up rather than silently patched on an unrelated branch.
- 30 new tests (175 total in `ai_agents/`), one per (corrected) spec Acceptance Criterion plus the driver-impersonation and trip-audit heuristic behavior. All passed on the first run.

## 2026-09-22 — Driver & Vehicle Assignment Agent: verified then implemented

- `ai_agents/specs/assignment-agent.md` had the same no-plan, no-verification profile as the two specs before it, and needed the largest factual correction of the three: **there is no `/api/v1/assignments` resource at all.** The real endpoints are vehicle-scoped (`POST /api/v1/vehicles/{vehicle_id}/assign`, `POST /api/v1/vehicles/{vehicle_id}/release` — not `PUT /api/v1/assignments/{id}/terminate`, and no assignment `id` is ever needed since at most one assignment is active per vehicle at a time) and reads are always scoped to one driver or one vehicle (`GET /api/v1/drivers/{id}/assignments`, `GET /api/v1/vehicles/{id}/assignments`) — there's no flat list-everything endpoint.
- RBAC for writes matched the draft exactly (`admin`/`fleet_manager`); reads were broader than claimed — a driver can view *any* vehicle's assignment history (only *their own* driver-history lookup is row-restricted server-side), not just "their own active pairing" as the draft framed it.
- The backend already enforces both assignment conflicts and the release-with-nothing-active case itself (`409`/`404`), so the agent's conflict pre-check (`agents/assignment/conflict_checker.py`) is explicitly a fail-fast layer with the backend's own row-checks as the race-safe backstop — same pattern as the Fleet Registry Agent's duplicate-plate handling.
- Caught a real design flaw in my own first pass via the test suite, not just in the source spec: the RBAC gate for `assign_asset`/`terminate_assignment` was originally only checked inside `validating_conflicts` (the first *gated* tool call in the flow) — but `resolving_entities`, which runs first, calls `get_vehicles_tool`/`get_drivers_tool`, both *ungated* reads. A driver or mechanic's write attempt would've cost two real backend round-trips before ever being blocked, violating the spec's own "refuses before making any backend call." Moved the check into `classify_intent`, before any tool call at all.
- 29 new tests (221 total in `ai_agents/`), one per corrected Acceptance Criterion plus the RBAC-ordering fix. Two failures on the first run: one was a trivial test-fixture bug (duplicate kwarg), the other was the RBAC-ordering flaw above — exactly the kind of thing this project's testing discipline exists to catch before it ships.
- Merged all six agent branches (`fleet-registry-agent` through `assignment-agent`) into `ai-agents` -- a clean fast-forward, since they formed one linear chain rather than diverging. Deleted all six local and (where pushed) remote feature branches after confirming `git branch -d` saw each as fully merged.

## 2026-09-22 — Grand Orchestrator: a genuinely different kind of spec, verified live

- `ai_agents/specs/grand-orchestrator.md` asks for something structurally new: a ReAct meta-agent (LLM-driven tool-calling and routing) sitting on top of the six deterministic sub-agents, with LangGraph `interrupt_before`-based human-in-the-loop and a Pydantic retry wrapper. Unlike the four prior "found on disk" specs, its core technical claims held up under implementation -- `interrupt_before`, `MemorySaver`, `update_state`/`get_state` all work exactly as described. The one real correction: the spec named Llama-3-70B/8B as the routing LLM, which isn't on this Groq account (same class of gap as the vision-model mismatch found on the Fleet Registry Agent) -- but unlike vision, a real smoke test found **tool-calling genuinely works** on `openai/gpt-oss-20b`/`120b`, so this agent could be verified live, not just mocked.
- Read every one of the other five agents' `graph.py` files to find their *real* mutating node names for `interrupt_before` -- the spec's FR 4 only gave three "e.g." examples. Real set: foundation→`creating`; fuel→`creating`,`creating_trip`; maintenance→`creating_log`,`creating_report`,`restocking`; accountability→`creating`; assignment→`executing`; insights→none (it's read-only, confirmed against its own spec's "no write operations" constraint). Added `tests/test_orchestrator_registry.py` to assert these against each graph's real `.nodes` dict, so a future node rename fails loudly instead of silently disabling that agent's HITL gate.
- Architecture: `orchestrator/runner.py`'s `SubAgentRunner` compiles each agent's *unmodified* `build_*_graph()` factory with its own `MemorySaver` + `interrupt_before`, per the spec's "Sub-Agent Immutability" constraint -- zero lines changed in any `agents/*/graph.py`. The orchestrator's own loop does NOT use LangGraph's checkpoint/resume on itself, only on each sub-agent; `OrchestratorSession.approve()/reject()/modify()` resume the sub-agent's own thread, append the observation, and re-invoke the orchestrator graph fresh from its `plan` entry point -- simpler than nesting interrupt/resume across two graph layers, verified live.
- Caught a real bug in my own first pass via the test suite: `execute_tool` was calling `validate_tool_args(..., attempt=1)` hardcoded on every hop, so `MAX_RETRIES` (FR 7) could never actually be reached -- a malformed tool call would retry forever instead of hard-faulting after 2 attempts. Root cause: I was returning bookkeeping keys (`_tool_retry_counts`, `_pending_image_bytes`, `_pending_mime_type`) that were never declared in `OrchestratorState`'s `TypedDict` -- **LangGraph silently drops any key a node returns that isn't declared in the state schema**, it's not an error. Every other agent's state.py already followed this discipline by declaring every field it touches; I broke it here without realizing why it mattered until the retry-exhaustion test's timing came out wrong. Fixed by declaring all three fields explicitly.
- Live-verified end-to-end (not just scripted): "find the worst-health vehicle with no active assignment and assign it to Jane Smith" against a fake backend with the real Groq LLM correctly chained `insights`→`assignment`(conflict check)→`foundation`(resolve odometer)→`assignment`(the write, which paused for approval) -- including a genuine self-correction mid-run when a `driver_history` call failed for a missing `query_driver_id`, recovering by resolving the driver's ID first. `approve()` resumed the real paused thread and completed the write; the synthesis correctly cited the actual created record. A second live session with a `driver`-role token had its fleet-health request correctly refused and explained, not silently bypassed or falsely reported as successful.
- 22 new tests (243 total in `ai_agents/`), all deterministic (scripted fake LLM + fake runner, no network call) except the live verification above, which was run manually and is not part of the committed suite since a live LLM's exact tool choice isn't something `pytest` can assert on deterministically.

## 2026-09-23 — FleetLiveObserver: a spec that conflicted with an existing hard rule

- `ai_agents/specs/fleet-live-observer.md` asked for something that isn't just factually off (like the last several) but actively conflicts with an architectural rule already established for every other agent in this codebase: its §5 "Data Lifecycle & Retention" wants direct PostgreSQL + S3/Parquet persistence from the telemetry hook, but root `CLAUDE.md` and `ai_agents/CLAUDE.md` both say `ai_agents/` never writes to the database directly, only through the backend's REST API -- and no telemetry endpoint exists there. Resolved by making the observer's `sink` an injectable async callable defaulting to local `logging` (which is FR 6's own stated fallback anyway, not a new invention), documented explicitly as a one-line swap once a real backend endpoint exists -- not silently built around, not silently ignored.
- Second real finding: `on_tool_start`/`on_tool_end` don't fire automatically just by attaching an `AsyncCallbackHandler` to a graph run, because `orchestrator/graph.py`'s `execute_tool` node dispatches sub-agents itself (reads `tool_calls` off the LLM response, calls `SubAgentRunner` directly) rather than through LangChain's own tool-execution runtime -- there's no real `Tool.run()` call anywhere for a callback to attach to. `FleetLiveObserver` ended up with two entry points into the same redaction/schema logic: the real `AsyncCallbackHandler` interface (verified against the installed `langchain-core`'s actual method signatures, for a future async execution path) and a plain sync recording API (`record_node`, `start_tool_call`, `record_tool_result`, `record_llm`) that `graph.py` calls explicitly today.
- A subtler redaction correctness issue caught before it became a bug rather than after: `graph.py`'s existing `_format_observation()` builds the LLM-facing scratchpad text via `repr()` on raw sub-agent state -- which the LLM is *supposed* to see unredacted (redaction is for the audit trail, not the model's own reasoning context). Wiring the observer naively off that already-formatted string would have meant nothing was ever actually redactable (a formatted string has no dict keys left to redact by). `record_tool_result()` instead takes the raw sub-agent state (`raw_result`) as a separate parameter and redacts *that* independently for the stored trace, leaving the scratchpad's unredacted text untouched.
- Wired additively: `OrchestratorDeps.observer` defaults to `None`, and every one of the 243 pre-existing tests passes completely unchanged. 36 new tests (279 total in `ai_agents/`), including two end-to-end integration tests proving the observer is actually reached during a real (scripted) orchestrator run -- not just unit-testable in isolation -- and that a HITL pause/resume round-trip correctly shares one `trace_id` across both halves (FR 4: a trace_id is per session *turn*, and approval is part of the turn that paused, not a new one). All passed on the first run.
