## 2026-09-21 — Fleet Registry Agent: spec, then implementation

- Wrote `ai_agents/CLAUDE.md`, the module-level directive file for `ai_agents/`, covering the MCP tool catalog, safety-hook enforcement, memory, and the cross-module HTTP-only boundary with `backend/`.
- Ran the `spec` skill against `ai_agents/Plans/Fleet Regitry Agent.md` (the Spec 00 onboarding-agent plan) to produce `ai_agents/specs/fleet-registry-agent.md`. The interview surfaced three scope decisions the plan left implicit, confirmed with the user: (1) supplier onboarding gets its own vision-extraction skill (`extract_supplier_doc`), not just vehicles/drivers; (2) update/edit of existing records stays out of scope for this agent (create + read only); (3) a vehicle document missing `fuel_type` (a required backend field no registration card states) is resolved by asking the user in-chat, not defaulting or hard-rejecting.
- Implemented the spec on branch `fleet-registry-agent`:
  - `tools/api_client.py` — `call_backend()`, the only path from `ai_agents/` to the FastAPI backend.
  - `tools/auth_context.py` — reads (never verifies) the caller's JWT for agent-layer RBAC gating and org-scoping; the backend's own signature check and live DB role re-check remain the actual security boundary.
  - `tools/schemas.py` — Pydantic v2 models duplicating the backend's create schemas' minimal shape (per the cross-module boundary rule) plus the three vision-extraction output schemas.
  - `tools/sanitize.py` — plate/VIN/phone/name/license-number normalizers, applied before any bridged payload reaches a create tool.
  - `tools/file_parsers.py` — added `extract_license_data`, `extract_vehicle_doc`, `extract_supplier_doc`, all Groq vision calls forced through `.with_structured_output()`.
  - `core/llm_config.py` — added `GROQ` and `LLAMA_API` providers (both OpenAI-compatible endpoints, same lazy-import pattern as the existing three providers).
  - `mcp_server/foundation_tools.py` (not `ai_agents/mcp/`, deliberately — that package name collides with the installed `mcp` SDK on `sys.path`, per the existing `NOTE` in `ai_agents/mcp/server.py`) — the six get/create tool wrappers, each write tool RBAC-gated via `auth_context.can_write` before any backend call.
  - `agents/foundation/` — `state.py` (`FoundationAgentState`), `license_inspector.py`, `duplicate_checker.py`, `router.py` (structural Onboard/Query classification by image presence, not an LLM call — the signal is already unambiguous), and `graph.py` wiring it all into a LangGraph state machine with every external dependency injected via `FoundationAgentDeps` for testability.
- Test suite: 69 tests (`uv run pytest` equivalent — `python -m pytest` against a scratch venv with the new deps installed), including one end-to-end graph test per Acceptance Criterion in the spec, using an in-memory fake `call_backend` rather than a live backend/Postgres. Caught and fixed two real bugs this way: PyJWT's `verify_signature: False` silently disables `verify_exp` too unless re-enabled explicitly; and the vision-extraction mime-type check was running *after* the (mocked) LLM client was constructed instead of before, which would have cost a real Groq call on every rejected upload.
- Manually verified end-to-end against a real running backend + Postgres (seeded a dedicated test org with one user per role via `backend/seed_test_users.py`, real signed JWTs, real Groq key). Found the Groq account has no vision-capable model available (`/v1/models` lists only text/audio models), so live vision extraction couldn't be exercised — ran the rest of the pipeline (RBAC, duplicate/expiry checks, backend calls) for real with the vision step faked.
- Found and fixed a real cross-branch problem: the repo's checked-out branch had silently changed (`frontend`, not `fleet-registry-agent`) between turns, so a CORS-middleware fix landed on the wrong branch, and `frontend` and `fleet-registry-agent` had diverged (frontend had the login/copilot UI + a scaffold-only backend; fleet-registry-agent had the full backend + no UI). Merged `fleet-registry-agent` into `frontend` (270/270 backend tests + 69/69 ai_agents tests still pass) to get one branch with both halves.
- Added `backend/app/main.py`'s CORS middleware (`cors_origins` setting, defaulting to `http://localhost:3000`) — without it the browser blocks every request from the Next.js dev server before it reaches a route, surfacing as an opaque network error.

## 2026-09-22 — Fuel Vision & Leakage Auditor Agent: spec, then implementation

- Wrote `ai_agents/specs/fuel-agent.md` from `ai_agents/plans/Fuel_Agent.md`, verifying every assumption against the real backend rather than transcribing the plan. Found and corrected: endpoint paths (`/api/v1/fuel`, `/api/v1/trips`, not `/fuel-logs`/`/trip-logs`); write roles (`admin`+`driver` only — the plan included `fleet_manager`, but the real `_WRITE_ROLES` on both routers excludes it); a required `price_per_liter` field the plan's extraction schema never produces (derived instead as `total_cost / liters_filled`); a missing plate→vehicle_id resolution step the plan's flow diagram skipped entirely; and a real backend gap where `/api/v1/trips` (unlike `/api/v1/fuel`) never forces `driver_id` to the caller's own profile for a driver-role caller — scoped the agent to compensate for it.
- Implemented on branch `fuel-agent` (off `frontend`, post-merge): `agents/fuel/{state,graph,efficiency_auditor}.py`, `mcp_server/fuel_tools.py` (its own role-gating logic, deliberately not reusing `foundation_tools`'s `can_write()` since the permitted roles differ per resource), `tools/schemas.py` additions (`FuelReceiptExtraction`, `FuelLogCreateInput`, `TripLogCreateInput`), and `tools/file_parsers.extract_fuel_receipt`.
- Anomaly detection (`is_anomalous`, `cost_per_km`) is deliberately never recomputed client-side — the backend already computes both, so the agent only surfaces that response field, avoiding two possibly-drifting calculations.
- 36 new tests (105 total in `ai_agents/`), one per Acceptance Criterion for the graph. Caught one real bug this way: plate-number matching used plain `.upper()` instead of the same `sanitize_plate_number` normalization used when vehicles are actually stored, so a legitimately matching plate (e.g. extracted as `"abc 123"` against a stored `"ABC-123"`) would have failed to resolve.

## 2026-09-22 — Maintenance & Parts Inventory Agent: spec, then implementation

- Wrote `ai_agents/specs/maintenance-inventory-agent.md` from `ai_agents/Plans/Maintenance_Inventory_Agent.md`, again verifying every assumption against the real backend rather than the plan. This one needed more correction than Fleet Registry or Fuel: (1) RBAC is asymmetric per resource, not one shared role set — maintenance writes are `admin+mechanic` (fleet_manager is read-only there), inventory writes are `admin+fleet_manager` (mechanic is read-only there), and `driver` has zero access to either, contradicting the plan's "driver gets read-only history" claim; (2) maintenance logging is genuinely a two-backend-call flow, not one — `MaintenanceLogCreate` has no `parts_used` field at all; parts consumption only happens via a separate `MechanicReportCreate` call to `POST /api/v1/maintenance/{log_id}/mechanic-report`, which is also where the backend row-locks and decrements stock (`SELECT ... FOR UPDATE`, rejects with `400` on insufficient stock); (3) `labor_hours` has no backend field, folded into `description` instead; (4) the plan's inventory-restock path (`PUT /inventory/{part_id}` with an absolute `qty_on_hand`) is real but non-atomic and race-prone — flagged as a known limitation rather than silently presented as solved, since the backend's actual properly-locked restock path is the separate `PurchaseOrder` → `/receive` flow, out of scope here.
- Implemented on branch `maintenance-inventory-agent` (off `fuel-agent`): `agents/maintenance/{state,graph,stock_checker}.py`, `mcp_server/maintenance_tools.py` (its own two write-role sets, plus — unlike the other two agents — client-side read gating too, since the spec's driver-refusal edge case covers all six tools, not just writes), `extract_work_order`/`extract_parts_invoice` (each accepting either an image or plain text, since typed mechanic notes don't need a vision call), and the associated schemas.
- 40 new tests (145 total in `ai_agents/`), one per spec Acceptance Criterion for the graph. All passed on the first run — the extra rigor spent verifying the spec against the real backend up front paid off here.

## 2026-09-22 — Driver Accountability & Asset Misuse Agent: verified then implemented

- `ai_agents/specs/driver-accountability-agent.md` was already present on disk, unlike the other three agents' specs, which I wrote myself after running the interview/verification pass. This one read like an unverified plan wearing a spec's filename (hedged language like "`GET /api/v1/drivers/safety` (or equivalent analytics endpoints)"), so I checked it against the real backend before implementing rather than trusting the filename.
- Found one finding more serious than any prior agent's: **FR 3 ("Misuse & Geofence Auditing") is architecturally impossible as written.** The root `CLAUDE.md` constraint is explicit — no real-time hardware, IoT, or GPS integration anywhere in this system — and there is no geofence, shift-schedule, or "authorized operating bounds" data model anywhere in the backend to audit against. Reframed as `agents/accountability/misuse_auditor.py`: a plain time-window heuristic over each `TripLog`'s existing `start_time`/`end_time` (flag trips outside a configurable hour window), explicitly documented as a heuristic proxy for human review, not real misuse detection.
- `get_driver_safety_tool` doesn't exist as a backend endpoint (the plan's own hedge was correct to worry). Replaced with `get_driver_timeline_tool` wrapping the real `GET /api/v1/drivers/{id}/timeline` (already aggregates trips/reports/incidents), with the agent aggregating incident counts by severity from that response — a genuine capability instead of a guessed URL.
- RBAC was more permissive in reality than the spec claimed: `/api/v1/incidents`' real roles are `(admin, fleet_manager, driver)` for **both** create and read — a driver can read their own incidents (row-filtered server-side), not just submit them. Only `mechanic` is excluded. Corrected `mcp_server/accountability_tools.py` accordingly rather than implementing the spec's stricter, inaccurate claim.
- `IncidentLogCreate.incident_type` is required and has no field the plan's extraction schema asks for; added it to `IncidentExtraction` with a `damage` default when unmappable (matching the plan's own implicit framing, since its only extraction target was `damage_description`).
- **Found a real bug in the already-shipped Fuel Agent while building this one's driver-impersonation guard correctly:** `Driver.id` is a separate primary key from `Driver.user_id` (which FKs to `User.id`). `agents/fuel/graph.py`'s trip-log path (via `mcp_server/fuel_tools.py`) overrides a driver-role caller's `driver_id` to `context.user_id` — but that's the `User.id` from the JWT's `sub` claim, not the caller's `Driver.id`. `TripLogCreate.driver_id` expects a `Driver.id`. This agent's own driver-impersonation guard (`_own_driver_id` in `agents/accountability/graph.py`) does it correctly: looks up the `Driver` row whose `user_id` matches the caller's `user_id` first. The Fuel Agent's bug was **not** fixed in this pass — flagged to the user as a follow-up rather than silently patched on an unrelated branch.
- 30 new tests (175 total in `ai_agents/`), one per (corrected) spec Acceptance Criterion plus the driver-impersonation and trip-audit heuristic behavior. All passed on the first run.
