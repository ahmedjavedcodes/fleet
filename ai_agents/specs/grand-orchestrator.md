# Spec: Grand Orchestrator

*Verified and executed directly (no separate plan document existed). Unlike the four "found on disk" specs before it, this one's core technical claims held up under implementation — `interrupt_before`, `MemorySaver`, and `update_state`/`get_state` all work exactly as described. The one real correction is the named LLM tier; everything else below documents load-bearing implementation decisions the spec left open, verified against a live model, not just mocks.*

## Problem Statement

Unchanged from the original: six deterministic sub-agents need a single ReAct controller that translates natural language into their exact structural inputs, chains them across hops, and enforces human approval before any write. Confirmed real and necessary by building it — see Acceptance Criteria.

## Functional Requirements — verified, with corrections

1. **ReAct hub-and-spoke routing**: implemented as `orchestrator/graph.py`'s `plan → execute_tool → (loop | synthesize)` `StateGraph`. The six sub-agent graphs are exposed as `StructuredTool`s (`orchestrator/tools.py`) whose `func` is a stub — `execute_tool` intercepts the LLM's `tool_calls` and dispatches itself, since dispatch needs the shared `SubAgentRunner`/`auth_context`, not just raw arguments.
2. **Immutable RBAC injection**: `OrchestratorSession.__init__` calls `build_context(token)` once and stores `{token, role, user_id, organization_id}` in `state["auth_context"]`. The routing LLM only ever sees `SystemMessage`/`HumanMessage`/`ToolMessage` content built from `chat_history` and `scratchpad` (`_history_to_messages`) — `auth_context` never enters that text. Verified live: a `driver`-role session's fleet-health request was refused with the real RBAC halt reason, not silently bypassed.
3. **Structural intent forcing**: six Pydantic models (`orchestrator/tool_schemas.py`), one per sub-agent, each `extra="forbid"`, whose fields are exactly that sub-agent's own state keys (e.g. `AssignmentToolInput.assign_request` → `AssignmentAgentState.assign_request` verbatim). `image_bytes`/`mime_type` are deliberately **not** LLM-fillable fields on any schema — an LLM cannot usefully emit raw image bytes as a tool argument; when the current turn has an attachment, `execute_tool` attaches it itself onto whichever sub-agent state the LLM's `document_type` selects.
4. **HITL write intercepts**: `SubAgentRunner` (`orchestrator/runner.py`) compiles each sub-agent's *unmodified* `build_*_graph()` factory with a fresh `MemorySaver` and `interrupt_before=<that agent's real mutating nodes>`. **The spec's FR 4 only gave three example node names ("e.g. `executing`, `creating`, `restocking`") — the real, complete set per agent, found by reading each `graph.py`'s `add_node` calls, is:** foundation → `creating`; fuel → `creating`, `creating_trip`; maintenance → `creating_log`, `creating_report`, `restocking`; accountability → `creating`; assignment → `executing`; **insights → none (it's read-only, never pauses)**. `orchestrator/registry.py` encodes this list per agent, and `tests/test_orchestrator_registry.py` asserts every one of them is a real node in its graph — a change to any `agents/*/graph.py` node name now fails that test instead of silently never triggering its interrupt.
5. **Multi-hop scratchpad**: `OrchestratorState.scratchpad`, a list of `{hop, tool, args, observation}`. Verified live in the same run: hop 1's `insights` observation (worst health score → `v-old`) was available for hop 2's `assignment` call to reference.
6. **Halt-aware state evaluation**: a halted sub-agent result becomes a scratchpad observation (`"{agent} halted: {halt_reason}"`) and the loop continues to `plan` — the LLM decides whether to explain or try something else, rather than the orchestrator hard-stopping. Verified live: the driver-role halt above was correctly explained, not silently dropped or retried.
7. **Pydantic retry wrapper**: `orchestrator/retry.py`'s `validate_tool_args`, called from `execute_tool` with a per-tool-name attempt counter (`state["_tool_retry_counts"]`) that resets on success and increments on failure — **this counter is real bookkeeping state, not spec-named, and had to be added to `OrchestratorState`'s `TypedDict` explicitly; LangGraph silently drops any key a node returns that isn't declared in the state schema**, which is exactly the bug that made the first draft of this wrapper never actually reach `MAX_RETRIES` (see prompts.md). `MAX_RETRIES = 2` per FR 7.
8. **Final synthesis layer**: a dedicated `synthesize` node, called once the LLM's `plan` response carries no more tool calls (or after a hard-fault). This costs one extra LLM call beyond what a naive ReAct loop needs (the `plan` call that decides "no more tools" produces a discarded response; `synthesize` then generates the real user-facing text) — a deliberate trade matching the spec's explicit ask for a distinct terminal synthesis step, not a bug.

## Constraints — one correction

- **LLM tiering: the spec's named model doesn't exist on this account.** Llama-3-70B/8B is not in this Groq key's `/v1/models` listing (see `prompts.md`'s Fleet Registry Agent entry for the same finding on the vision side). Tool-calling **was verified live and works** on `openai/gpt-oss-20b` and `openai/gpt-oss-120b` — `core/llm_config.py`'s `GROQ` provider now defaults orchestrator calls to `openai/gpt-oss-20b` (smaller/faster, matching "low-latency" better than the 120b variant), configurable the same way as the vision model.
- **Zero-waste sub-agents**: unaffected — every sub-agent graph is exactly as expensive as it was standalone; the orchestrator adds no LLM cost inside them.
- **Sub-agent immutability**: held exactly as specified. `SubAgentRunner` calls each agent's existing `build_*_graph(deps)` factory (already exported by every agent for testability) and only adds a checkpointer + `interrupt_before` at compile time — zero lines changed in any `agents/*/graph.py`.
- **Added, not in the original spec**: a hop-count ceiling (`MAX_HOPS = 8`) in the `plan` node. Nothing in the spec bounds the ReAct loop, and an unbounded loop against a live, billed LLM is a real cost/availability risk — verified via a scripted-LLM test that a runaway loop halts cleanly instead of looping forever.

## Behaviour — one architectural note beyond the spec's diagram

The spec's `multi_hop_with_hitl` diagram shows the HITL interrupt as a step inside one continuous flow. In practice, **the orchestrator's own graph does not use LangGraph's checkpoint/resume on itself** — only each *sub-agent's* graph is checkpointed. When `execute_tool` sees `awaiting_approval`, the orchestrator's `StateGraph.invoke()` call simply returns (routes to `END`) with `state["hitl_state"]` populated. `OrchestratorSession.approve()/reject()/modify()` resume the *sub-agent's* thread via `SubAgentRunner.resume()`, append its result as a new scratchpad entry, and call `self._graph.invoke()` **fresh** — since the entry point is `plan`, this naturally continues the ReAct loop with the LLM seeing the just-resolved observation. This is simpler than nesting the orchestrator's own graph inside a checkpointed interrupt/resume cycle, and was verified live: `approve()` after a real pause correctly resumed and completed the write.

## Edge Cases and Error Handling — verified

| Trigger | Verified Behaviour |
|---|---|
| User modifies a field during a HITL pause | `OrchestratorSession.modify(updates)` calls `SubAgentRunner.resume(..., updates=updates)`, which calls the sub-agent graph's real `update_state(config, updates)` before resuming — confirmed via a real assignment graph pause+modify+resume in `tests/test_orchestrator_runner.py` (a genuine `interrupt_before`/checkpointer round-trip, not a mock). |
| User rejects a HITL prompt | `reject()` never calls `SubAgentRunner.resume()` at all — the paused thread is simply abandoned (`MemorySaver` is in-process and per-session; nothing further is persisted). An abort observation is appended and the loop continues to `plan`/`synthesize` for a natural-language confirmation. |
| Sub-agent returns `halt_reason` | Delivered to the scratchpad as an observation; verified live end-to-end (driver RBAC halt → correct natural-language explanation, no false success claim). |
| Orchestrator LLM generates malformed tool arguments | `ToolValidationError` observation fed back; verified that retries genuinely count down and a 3rd consecutive failure on the same tool hard-halts without ever reaching the sub-agent (`runner.run_calls == []` in that test). |

## Acceptance Criteria — all verified, three live against the real Groq model

1. **Verified live** (not just scripted): "find the worst-health vehicle with no active assignment and assign it to Jane Smith" correctly sequenced `insights` (fleet_health) → `assignment` (vehicle_history, to confirm no conflict) → `foundation` (vehicles, to resolve the odometer) → `assignment` (the write, which paused) — all without redundant human prompting between hops.
2. **Verified live and via `test_orchestrator_runner.py`**: a sub-agent reaching its mutating node suspends (`StateSnapshot.next` non-empty) and yields a structured `hitl_state` payload (`agent_name`, `thread_id`, `pending_node`, the paused sub-agent's own state) — this *is* what a frontend would render for approval.
3. **Verified live**: `approve()` resumed the exact paused thread (same `thread_id`) and completed the real write, producing an accurate synthesis citing the actual created record.
4. **Verified live and via `test_fr2_*`**: the session's real role/user_id reached the sub-agent's `AgentContext` unchanged, and the routing LLM's own message history never contained the raw token.
5. **Verified live for both a completed write and a halted RBAC denial**: `synthesize` produced a context-aware, accurate natural-language summary in both cases — including correctly *not* claiming success when the operation was blocked.
