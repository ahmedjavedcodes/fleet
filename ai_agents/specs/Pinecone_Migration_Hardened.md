# Pinecone Migration Architecture: Hardened V2 Specification

This specification addresses the six security, operational, and lifecycle gaps identified in the Pinecone migration plan.

> **Implementation status (2026-09-24): executed, verified live.** Where the code
> differs from the text below, a **Correction** note says why. Architecture as
> built:
>
> - **The backend owns Pinecone**, not `ai_agents/`. The spec already places the filter
>   factory in `memory_service.py`, a backend file, and the DLQ in Postgres. More
>   importantly, `ai_agents/` reads JWT claims *unverified*, so an org filter built
>   there could be forged. The backend verifies the token first.
> - **Postgres stays the system of record** for every memory (content, scope, owner,
>   `is_active`). Pinecone holds only vectors plus filter metadata (never the memory
>   text), under id `"<organization_id>#<memory_id>"`. Every vector hit is re-checked
>   against Postgres before it is returned.
> - **pgvector is gone.** The `vector(768)` column and the `CREATE EXTENSION` were
>   removed from the (never-applied) memory migration, so stock Postgres works again.
> - Dedicated serverless index `fleet-memory` (768-dim, cosine, aws/us-east-1),
>   created by `backend/scripts/create_pinecone_index.py`. The account's other index
>   (`digisinc`) was not touched.

## 1. RBAC Enclosure & App-Layer Defense-in-Depth

### Known Trade-Off

Moving vector search out of PostgreSQL removes database-enforced Foreign Keys and Row-Level Security (RLS). Tenant isolation rests entirely on application logic within `memory_service.py`.

### Hardened Control

To prevent single-point-of-failure regressions, all vector query payloads must be generated by a mandatory, centralized helper function that cannot be bypassed.

```python
# memory_service.py

def _build_rbac_filter(context: AgentContext, extra_filters: dict | None = None) -> dict:
    """Centralized filter factory. 
    Guarantees organization_id is ALWAYS present on every Pinecone operation.
    """
    if not context.organization_id:
        raise ValueError("Security violation: AgentContext missing organization_id")
        
    filters = {"organization_id": context.organization_id}
    
    if context.role not in ("admin", "fleet_manager"):
        # Non-admins can only search personal memories or entity memories
        filters["$or"] = [
            {"scope": "personal", "user_id": context.user_id},
            {"scope": "entity"}
        ]
        
    if extra_filters:
        filters.update(extra_filters)
        
    return filters
```

**Correction — the sketch above has three security bugs, fixed in
`backend/app/services/vector_store.py::build_rbac_filter`:**

1. For `admin`/`fleet_manager` it adds no scope clause, so managers could read
   **everyone's personal memories**, a regression from agent-memory.md. Personal
   facts are now owner-only for every role.
2. For other roles it omits `organization` scope, hiding org-wide facts (e.g. "company
   currency is PKR") from drivers and mechanics. Now visible to the whole org.
3. `filters.update(extra_filters)` lets an extra `organization_id` or `$or` key
   **replace** the security clauses. Extras are now ANDed (`{"$and": [org_pin,
   visibility, *extras]}`), so they can only narrow results.

It also takes the backend `User` (from the verified token), not an `AgentContext`.

- **Runtime Enforcer:** A middleware hook validates that every outgoing request to Pinecone's `index.query()` or `index.delete()` includes `organization_id`. Any query lacking this key aborts immediately and logs a `CRITICAL` security alert.
  - *Built as `OrgScopeGuard`*, which wraps every store (tests included). It requires
    the org pin at the top level or as a direct `$and` member; a pin inside an `$or`
    doesn't count, since the sibling branch bypasses it. It also covers `update`
    (and refuses rewriting `organization_id`), `upsert` (id prefix must match the
    metadata's org) and `fetch` (every id must carry the caller's org prefix).

## 2. Retention, Dedup, and Staleness Lifecycle

### Staleness Policy

- **Soft-Delete on Supersede:** When a new entity fact supersedes an old one (e.g., new transmission repair on vehicle `ABC-123`), the older vector metadata is updated to `is_active: False`. It is immediately excluded from `fetch_memory` via the active query filter (`"is_active": True`).

### Monthly Dedup & Pruning Cron

A scheduled job executes on the first of every month:

*Correction: no scheduler exists in this project. The job is
`python -m app.jobs.memory_maintenance` (all orgs; schedule it with cron `0 3 1 * *`
or Windows Task Scheduler), plus admin-only `POST /api/v1/memory/memories/dedupe`
and `/prune` for a single org. The table is `semantic_memories`, not
`agent_memories`.*

1. **Deduplication:** Iterates through `agent_memories` by `organization_id`, computing cosine similarity between vectors. Pairs exceeding a `0.98` similarity threshold are merged, keeping the newest vector ID and deleting the duplicate.
2. **Hard Pruning:** Permanently purges vectors flagged as `is_active: False` older than 90 days using `index.delete(filter={"is_active": False, "updated_at": {"$lt": cutoff_timestamp}})`.
   - Verified live: delete-by-metadata-filter with a numeric `$lt` works on serverless.
     `updated_at` is stored as epoch seconds, since Pinecone range operators need
     numbers, and the filter is also org-pinned. The Postgres rows are kept as the
     audit trail; only the vectors are purged.
   - **Correction (found live):** Pinecone answers update-by-filter,
     delete-by-filter and `delete_all` on a namespace that has never been written
     with **404 "Namespace not found"**, while query and fetch return empty. The
     adapter treats that as a successful no-op. Otherwise the first prune on a fresh
     index would retry three times and dead-letter a false alarm.

## 3. Background Write Resiliency & Dead-Letter Queue (DLQ)

Vector operations executing on background thread pools enforce a strict 3-tier retry policy with exponential backoff:

```text
[Background Task] ──► Try 1 (Instant) ──(Fail)──► Try 2 (+1s) ──(Fail)──► Try 3 (+4s)
                                                                            │
                                                                         (Fail)
                                                                            ▼
                                                                  [Write to Postgres DLQ]
                                                                (failed_vector_jobs table)
```

- **Retry Ceiling:** Maximum 3 attempts (delays: 0s, 1s, 4s).
- **Postgres DLQ Table:** If all 3 attempts fail (e.g., network partition, bad payload), the event is written to `failed_vector_jobs` in PostgreSQL:
  - `job_id` (UUID), `organization_id`, `payload` (JSONB), `error_message`, `created_at`.
- **System Impact:** The user's active turn is unaffected. Administrators receive an alert if the DLQ depth exceeds zero.
  - *As built:* each job is plain JSON data (`op` + filters/vectors + namespace), so
    a DLQ row can be replayed verbatim. Every dead-letter logs an `ALERT` line with the
    current DLQ depth at ERROR level. Admin-only `GET /api/v1/memory/vector-jobs/failed`
    lists jobs and `POST .../{id}/retry` replays one; a job leaves the table only once
    its replay succeeds. The memory itself is never lost: it is written to Postgres
    before any vector work starts.
  - *Also found:* the first Pinecone call needs `describe_index`, which can fail on
    DNS (it did, repeatedly, on the dev machine). The store then degrades to
    Postgres-only for that request and retries initialization on the next one,
    instead of returning a 500.

## 4. Cost Model & Vendor Abstraction

### Cost Impact

- **Serverless Pricing:** Pinecone Serverless charges based on Read Units (RUs), Write Units (WUs), and Storage ($0.33/GB-month).
- **Projected Usage:** A 500-vehicle fleet generates ~5,000 memories/month (~3.5 MB of vector data). This easily stays within Pinecone's free tier allocation ($0/month) during initial rollout and scales to <$5/month under heavy production load.

### Vendor Isolation Strategy

To prevent long-term lock-in, all vector operations adhere strictly to an abstract `VectorStore` interface.

```python
class VectorStore(Protocol):
    def query(self, vector: list[float], top_k: int, filters: dict, namespace: str) -> list[dict]: ...
    def upsert(self, vectors: list[dict], namespace: str) -> None: ...
    def delete(self, filters: dict, namespace: str) -> None: ...
```

Swapping Pinecone for Qdrant, Milvus, or `pgvector` in the future requires modifying only the concrete `PineconeVectorStore` class inside `memory_service.py`.

*As built:* the protocol lives in `backend/app/services/vector_store.py` and adds
`update_metadata(filters, ...)` (the soft-delete) and `fetch(ids, organization_id, ...)`
(dedupe). `memory_service.py` never imports the Pinecone SDK.

**Embeddings:** the same key gives Pinecone Inference. `llama-text-embed-v2` supports
768 dims, matching the existing embedding contract, and is available in `ai_agents/`
as `MEMORY_EMBEDDER=pinecone`. **Calibration found live:** a correct paraphrase
match ("what currency should I show expenses in?" -> "User prefers ... PKR") scored
cosine distance **0.675**, above the backend's generic 0.5 cutoff, while an unrelated
fact scored above 0.8. `AgentMemory` therefore requests `max_distance=0.75`. This is
tuned on a single example and worth revisiting with real data.

## 5. Eventual Consistency Guarantee

### Window Acknowledgment

Async background upserts introduce an eventual consistency window of **100ms to 500ms** before a new vector is queryable via vector search.

### Read-Your-Own-Writes Mitigation

For HITL-approved `update_memory` calls, the system bypasses vector retrieval for the remainder of the active turn:

1. When the user approves `update_memory`, the response string (`"update_memory saved [organization scope]: User prefers cost reports in PKR"`) is appended directly to the Orchestrator's **scratchpad** for the current turn.
2. The routing LLM sees the fact in its scratchpad observations immediately, providing instant context awareness without waiting for the Pinecone index write to settle.

*Already true before this migration:* `session.py` appends `update_memory saved
(<scope> scope): <fact>` to the scratchpad on approval. The architecture adds a
second guarantee in the other direction. A soft-deleted memory is flipped
`is_active=False` in Postgres synchronously, and every Pinecone hit is re-checked
there, so a stale vector can never surface a retired fact, even while Pinecone's
metadata is still catching up (covered by
`test_deactivated_memory_is_hidden_even_if_pinecone_metadata_is_stale`).

## 6. Test Suite Isolation & CI Quota Protection

To prevent test suite flakiness, rate-limiting, and quota consumption:

- **Unit & Integration Tests (Mocked):** 95% of backend and agent tests use `unittest.mock` to mock the Pinecone client. Tests verify filter construction, failure fallbacks, and payload formatting without hitting external network endpoints.
- **End-to-End Live Tests (Isolated Namespace):** Live tests connecting to Pinecone execute against a dynamically generated UUID namespace:

```python
@pytest.fixture
def live_pinecone_namespace():
    test_namespace = f"test_ci_{uuid.uuid4().hex[:8]}"
    yield test_namespace
    # Teardown: Purge test namespace completely after run
    pinecone_index.delete(delete_all=True, namespace=test_namespace)
```

*As built:* an autouse fixture forces "no vector store" for every backend test, so
even with `PINECONE_API_KEY` in `backend/.env` nothing reaches Pinecone by accident.
Store-dependent tests opt into an in-memory fake that implements Pinecone's filter
semantics, sitting behind the real `OrgScopeGuard`. Live tests
(`tests/test_pinecone_live.py`) run only with `PINECONE_LIVE_TESTS=1`.
**Correction:** the teardown above raises 404 when a test never wrote to its
namespace; the fixture ignores that 404.
